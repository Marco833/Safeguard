# ADR-003 : Stockage du journal d'analyse avec SQLite

**Statut** : Accepté
**Date** : 15/09/2026
**Auteurs** : Naiim, Marc, Lenny

## Contexte
Le Jalon 1 exige un "journal cherchable" enregistrant, pour chaque fichier
analysé : son empreinte (hash), son type réel, son extension déclarée, sa
cohérence, et la date d'analyse. Ce journal doit permettre de retrouver et
d'interroger les analyses passées (ex. lors d'une investigation).

Il fallait choisir un système de stockage simple à mettre en place par une
équipe débutante, sans infrastructure serveur supplémentaire à gérer.

## Décision
Utilisation de SQLite via le module `sqlite3`, inclus nativement dans Python.

## Alternatives envisagées
- **PostgreSQL / MySQL** : rejeté pour le Jalon 1 — nécessite d'installer et
  d'administrer un serveur de base de données séparé, ce qui ajoute de la
  complexité (configuration, gestion des accès, sauvegarde) disproportionnée
  par rapport au volume de données du prototype.
- **Fichier plat (CSV ou texte)** : rejeté — ne permet pas de requêtes
  structurées (filtrer par type, par date, par cohérence) sans réécrire une
  logique de recherche à la main. Ne répond pas correctement à l'exigence
  "journal cherchable".

## Conséquences
**Avantages** :
- Aucune installation ni serveur à gérer : la base est un simple fichier
  (`journal.db`) sur le disque
- Requêtes SQL standards possibles (filtrage, tri, agrégation) dès le départ
- Inclus nativement dans Python (`import sqlite3`), aucune dépendance externe
- Suffisant pour le volume de données attendu dans le cadre du projet

**Limites / risques acceptés** :
- SQLite n'est pas conçu pour de multiples écritures simultanées à haute
  fréquence (plusieurs processus qui écrivent en même temps) — non
  problématique ici car le filtre mail traite les messages un par un
- Pas de gestion fine des droits d'accès utilisateur comme un vrai serveur
  de base de données (PostgreSQL) — à réévaluer si le projet évolue vers
  une architecture multi-utilisateurs pour le rendu final
- Le fichier `journal.db` doit être sauvegardé manuellement (pas de
  réplication automatique) — point à couvrir dans la procédure de
  sauvegarde/restauration exigée par le cahier des charges
